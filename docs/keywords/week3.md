# 1. Page와 Slice

- Page: 조회한 목록과 함께 전체 데이터 수, 전체 페이지 수를 제공하는 Spring Data의 반환 타입입니다. 전체 개수를 구하기 위한 COUNT 쿼리가 추가로 실행될 수 있습니다.
- Slice: 조회한 목록과 다음 목록의 존재 여부를 제공합니다. 전체 데이터 수와 전체 페이지 수는 제공하지 않으며, 이를 위한 COUNT 쿼리도 필요하지 않습니다.
- 다음 목록 확인: Slice는 일반적으로 요청한 개수보다 한 개 더 조회합니다. 10개를 요청했다면 11개를 조회하고, 응답에는 10개만 담으면서 나머지 한 개로 hasNext를 판단합니다.
- 차이: Page는 전체 목록에서 어느 위치인지 파악하기 좋고, Slice는 다음 데이터를 이어서 보여주는 데 적합합니다. Page도 다음 목록의 존재 여부를 제공합니다.
- 사용 시점: 전체 개수와 페이지 번호 이동이 필요한 게시판은 Page, 더 보기나 무한스크롤처럼 다음 목록만 필요한 화면은 Slice를 사용합니다.
- 주의점: Slice를 사용한다고 자동으로 커서 방식이 되는 것은 아닙니다. 일반적인 Pageable 기반 Slice도 offset을 사용하므로 반환 타입과 페이지네이션 방식은 구분해야 합니다. Page 역시 결과만으로 전체 개수를 알 수 있다면 COUNT 쿼리가 생략될 수 있습니다.

# 2. DB 인덱스

- 인덱스: 특정 컬럼 값을 기준으로 데이터를 빠르게 찾기 위한 별도의 자료구조입니다. 책의 색인처럼 전체 데이터를 확인하는 대신 필요한 위치에 접근하도록 도와줍니다. MySQL InnoDB의 일반적인 인덱스는 B-tree 계열입니다.
- 장점: 조건에 맞는 데이터 검색, 테이블 간 조인, 정렬 등의 성능을 높일 수 있습니다.
- 단점: 저장 공간을 사용하고, 데이터가 추가·수정·삭제될 때 인덱스도 함께 관리해야 합니다. 조회가 빨라지는 대신 쓰기 비용이 늘어날 수 있어 모든 컬럼에 인덱스를 설정하는 것은 좋지 않습니다.
- 설정 기준: 자주 실행되거나 느린 쿼리의 WHERE, JOIN, ORDER BY에 사용되는 컬럼을 먼저 살펴봅니다. 데이터 개수와 값의 분포, 조회 범위, 쓰기 빈도도 함께 고려합니다.
- 선택도: 조건에 맞는 행이 적을수록 인덱스로 조회 범위를 줄이기 유리합니다. 다만 값의 종류가 적은 컬럼도 특정 값이 드물거나 다른 컬럼과 조합하면 유용할 수 있습니다.
- 복합 인덱스: 여러 컬럼을 묶어 만든 인덱스입니다. 예를 들어 (category, created_at, id)는 카테고리별 게시글을 생성일 순서로 찾는 데 활용할 수 있습니다. 일반적으로 왼쪽부터 이어지는 컬럼 조건을 활용하기 좋으므로 컬럼 순서가 중요합니다.
- 활용 방법: DB 옵티마이저가 쿼리와 통계를 바탕으로 실행 계획을 선택합니다. 인덱스를 만들었다고 반드시 사용되거나 성능이 좋아지는 것은 아닙니다.
- 검증 방법: EXPLAIN으로 선택한 인덱스와 예상 조회 행 수를 확인하고, EXPLAIN ANALYZE로 실제 실행 시간과 처리 행 수를 비교합니다. EXPLAIN ANALYZE는 쿼리를 실제로 실행한다는 점에 주의해야 합니다.

# 3. 회원 탈퇴 시 게시글 처리와 게시글·댓글의 생명주기

- 생명주기: 데이터가 생성되고 사용되다가 삭제되는 과정입니다. 서로 연관되어 있다는 이유만으로 반드시 함께 삭제되어야 하는 것은 아닙니다.
- 게시글 함께 삭제: 개인 기록 서비스나 탈퇴 시 콘텐츠 삭제를 약속한 서비스에 적합합니다. 게시글뿐 아니라 다른 회원의 댓글, 첨부 파일, 검색 결과를 어떻게 처리할지도 정해야 합니다.
- 게시글 유지·작성자 익명화: 질문·답변과 토론을 보존하는 커뮤니티에 적합합니다. 작성자를 '탈퇴한 회원'으로 표시할 수 있지만, 회원 FK 처리와 본문·첨부 파일 속 개인정보도 함께 고려해야 합니다.
- 소프트 삭제: 데이터를 실제로 지우지 않고 삭제 상태로 표시하는 방식입니다. 복구나 후속 처리가 필요할 때 유용하지만, 정보가 그대로 남기 때문에 익명화나 접근 제한을 별도로 설계해야 합니다.
- 이용자 선택: 탈퇴 전에 게시글의 삭제·보존 여부를 선택하도록 할 수도 있습니다. 선택 가능한 범위와 삭제 완료 시점, 예외 정책을 명확히 안내해야 합니다.
- 회원과 게시글: 작성자가 탈퇴해도 게시글은 다른 이용자에게 유용한 정보로 남을 수 있습니다. 따라서 회원과 게시글의 생명주기를 분리하는 선택이 가능합니다.
- 게시글과 댓글: 댓글은 보통 특정 게시글에 달린 내용이므로 부모 게시글 없이 남으면 맥락을 잃기 쉽습니다. 게시글을 물리 삭제할 때 댓글도 함께 삭제하는 정책이 자연스럽지만, 반드시 그래야 하는 것은 아닙니다.
- 예외 상황: 다른 이용자의 댓글이나 답글을 보존해야 한다면, 원문을 '삭제된 게시글' 또는 '삭제된 댓글'로 바꾸고 관계를 남기는 방법도 있습니다.
- 대량 삭제: 게시글이 100개라 해도 댓글과 첨부 파일까지 포함하면 처리량이 커질 수 있습니다. 잠금 시간, 메모리 사용, 실패 시 복구와 동시에 들어오는 작성 요청도 고려해야 합니다.
- 제 의견: 개인 기록 서비스는 함께 삭제하는 방식이 적합하고, 커뮤니티는 게시글을 유지하면서 작성자를 익명화하는 방식이 적합하다고 생각합니다. 게시글과 댓글도 다른 사람의 대화가 연결되어 있다면 삭제 표시를 남기는 방법을 고려할 것 같습니다. 관계의 형태보다 서비스의 목적과 데이터가 독립적으로 의미를 가지는지를 기준으로 정하는 것이 좋다고 생각합니다. 추가적으로 이전에 이런 탈퇴한 사용자가 다시 재가입 하는 경우에 대해서도 고려해본 경험이 있는데 상당히 복잡했고 각각의 경우가 너무 나뉘는 경우 이를 디테일하게 분리해야 하는 경우도 있었습니다. 

# 4. DB 무결성과 Cascade

- 무결성: 저장된 데이터가 정해진 규칙을 만족하고 일관된 상태를 유지하는 성질입니다.
- 개체 무결성: 각 행을 유일하게 식별할 수 있어야 한다는 규칙입니다. PRIMARY KEY는 중복과 NULL을 허용하지 않습니다.
- 참조 무결성: 연관 데이터가 유효한 대상을 참조해야 한다는 규칙입니다. FOREIGN KEY로 존재하지 않는 부모를 참조하는 데이터를 막을 수 있습니다. NULL 허용 여부는 별도 제약으로 정합니다.
- 도메인 무결성: 값이 정해진 타입·범위·조건을 만족해야 한다는 규칙입니다. 컬럼 타입, NOT NULL, CHECK 등의 제약 조건으로 표현할 수 있습니다.
- UNIQUE: 컬럼이나 컬럼 조합의 중복을 제한하는 제약 조건입니다. 회원 이메일처럼 중복되면 안 되는 값을 관리할 때 사용합니다.
- Java와 DB의 검증: Java 검증은 애플리케이션에서 잘못된 입력을 막고, DB 제약 조건은 다른 프로그램이나 직접 실행한 SQL에도 적용됩니다. @Column(nullable = false)는 스키마 생성 시 NOT NULL을 표현하는 매핑 정보이며, 빈 문자열을 검사하는 기능은 아닙니다.
- DB Cascade: 부모 행의 변경이나 삭제를 자식 행에 전파하는 참조 동작입니다. ON DELETE CASCADE는 부모 삭제 시 자식도 삭제하고, ON UPDATE CASCADE는 참조 키가 바뀌면 자식 FK도 변경합니다.
- 다른 참조 동작: RESTRICT는 자식이 참조 중인 부모의 삭제를 거부하고, SET NULL은 부모 삭제 시 자식 FK를 NULL로 바꿉니다. SET NULL을 사용하려면 해당 컬럼이 NULL을 허용해야 합니다. MySQL InnoDB에서는 NO ACTION도 RESTRICT처럼 동작합니다.
- JPA Cascade: 한 엔티티에 적용한 영속성 작업을 연관 엔티티에도 전파하는 설정입니다. DB의 ON DELETE CASCADE와는 별개이며, 연관관계 애너테이션의 cascade 속성으로 지정합니다.
- PERSIST / MERGE: 각각 영속화와 준영속 객체의 상태 병합을 전파합니다.
- REMOVE: 부모 엔티티 삭제 시 연관 엔티티에도 삭제를 전파합니다. 부모와 자식의 생명주기를 함께 관리할 때 사용합니다.
- REFRESH / DETACH: 각각 DB 상태로 다시 읽기와 영속성 컨텍스트에서 분리를 전파합니다.
- ALL: 위 영속성 작업을 모두 전파합니다. 필요한 작업만 지정할지 먼저 판단해야 합니다.
- orphanRemoval: @OneToMany나 @OneToOne에서 부모와 관계가 끊어진 자식을 삭제하는 설정입니다. 예를 들어 관리 중인 게시글의 댓글 컬렉션에서 댓글을 제거하면 flush 시 삭제 대상이 됩니다. 부모 삭제 전파만을 의미하는 REMOVE와 차이가 있습니다.
- 사용 시점과 주의점: 게시글과 댓글처럼 생명주기가 종속된 관계에서 고려할 수 있습니다. 여러 엔티티가 공유하거나 독립적으로 존재하는 대상에는 무분별하게 적용하지 않습니다. 특히 게시글에서 작성자 방향으로 REMOVE를 설정하면 게시글 삭제가 회원 삭제로 이어질 수 있습니다. JPA에서 REMOVE의 이식 가능한 사용 범위는 @OneToOne과 @OneToMany입니다.
- 벌크 삭제: JPQL DELETE는 엔티티별 삭제와 달리 JPA 삭제 Cascade와 콜백을 거치지 않습니다. DB FK 제약과 DB Cascade는 별도로 적용되며, 영속성 컨텍스트와 DB 상태가 어긋날 수 있습니다.
- 트랜잭션: 여러 삭제 작업을 함께 성공하거나 취소하도록 서비스의 @Transactional로 경계를 정합니다. 기본적으로 RuntimeException과 Error는 롤백 대상이고, 체크 예외는 rollbackFor 등의 설정을 검토해야 합니다. flush는 SQL 반영 단계이며 커밋 완료와 같지 않습니다.
