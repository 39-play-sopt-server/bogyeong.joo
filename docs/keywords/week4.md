# 1. CI/CD

- CI/CD: 코드 변경을 통합하고 검증한 뒤 배포하기까지의 과정을 지속적으로 수행하는 개발 방식입니다. 빌드·테스트·배포 같은 반복 작업을 자동화해 변경 사항을 빠르고 안정적으로 전달하는 데 목적이 있습니다.
- CI(Continuous Integration, 지속적 통합): 여러 개발자가 변경한 코드를 공유 저장소에 자주 통합하고, 자동 빌드와 테스트로 문제를 조기에 확인하는 방식입니다. 오랫동안 따로 개발한 코드를 한꺼번에 합칠 때 생기는 충돌과 오류를 줄일 수 있습니다.
- CI의 흐름: 코드 push 또는 PR 생성 → 소스 코드 내려받기 → 실행 환경과 의존성 준비 → 빌드·테스트·정적 분석 → 결과 확인 순으로 구성할 수 있습니다. 검사에 실패하면 원인을 수정한 뒤 다시 검증합니다.
- Continuous Delivery(지속적 제공): 검증된 변경 사항을 언제든 운영 환경에 배포할 수 있는 상태로 유지하는 방식입니다. 배포 준비 과정을 자동화하되, 실제 운영 배포는 사람의 승인이나 결정으로 진행할 수 있습니다.
- Continuous Deployment(지속적 배포): 파이프라인의 검증을 통과한 변경 사항을 별도의 수동 승인 없이 운영 환경까지 자동으로 배포하는 방식입니다. CD는 문맥에 따라 지속적 제공과 지속적 배포 중 하나를 의미합니다.
- 차이: CI는 변경 코드를 통합하고 검증하는 데, CD는 검증한 결과물을 배포 가능한 상태로 만들거나 실제로 배포하는 데 초점을 둡니다. 빌드와 테스트만 자동으로 실행한다면 운영 배포까지 자동화했다고 볼 수는 없습니다.
- 파이프라인: 빌드·테스트·패키징·배포 같은 작업을 순서와 조건에 따라 연결한 실행 과정입니다. 앞 단계가 실패하면 배포를 중단하도록 설정할 수 있습니다.
- 도구: GitHub Actions, Jenkins, GitLab CI/CD 등으로 파이프라인을 구성할 수 있습니다. GitHub Actions는 저장소의 push나 PR 같은 이벤트를 기준으로 워크플로를 실행할 수 있습니다.
- 적용 예시: Spring Boot 프로젝트에서 PR이 열리면 Gradle로 빌드와 테스트를 실행하고, 기준 브랜치에 병합되면 검증한 JAR나 컨테이너 이미지를 서버에 배포하도록 구성할 수 있습니다. 이는 구성 예시이며 현재 저장소의 적용 상태를 의미하지는 않습니다.
- 주의점: 테스트가 통과해도 운영 환경에서 문제가 발생할 수 있습니다. 배포 후 상태 확인과 모니터링, 이전 버전으로 되돌리는 절차를 준비하고, 비밀번호나 배포 인증 정보는 코드에 직접 저장하지 않아야 합니다.

# 2. HTTPS를 적용해야 하는 이유

- HTTPS(Hypertext Transfer Protocol Secure): HTTP 통신에 TLS를 적용해 데이터를 안전하게 주고받는 방식입니다. HTTP 요청·응답의 의미는 유지하면서 전송 구간을 보호합니다.
- HTTP의 문제점: HTTP 자체는 통신 내용을 암호화하지 않습니다. 통신 경로에 접근할 수 있는 공격자가 비밀번호, 인증 토큰, 요청·응답 본문을 읽거나 내용을 바꿀 위험이 있습니다.
- 기밀성: 전송 데이터를 암호화해 제삼자가 통신 내용을 읽기 어렵게 합니다. 로그인 정보뿐 아니라 게시글 내용이나 API 응답도 보호 대상입니다.
- 무결성: 전송 중 데이터가 변조되었는지 탐지합니다. 공격자가 응답에 악성 코드를 삽입하거나 요청 내용을 몰래 바꾸는 공격을 방어하는 데 필요합니다.
- 서버 인증: 인증서와 TLS 핸드셰이크를 통해 접속한 서버가 요청한 도메인에 대한 유효한 인증 정보를 가지고 있는지 확인합니다. 암호화만 하고 상대를 확인하지 않으면 공격자가 중간에서 서버를 사칭할 수 있습니다.
- 적용 범위: 로그인이나 결제 페이지뿐 아니라 서비스 전체에 적용하는 것이 좋습니다. 일부 페이지만 보호하면 다른 페이지에서 전달되는 데이터가 노출되거나 페이지 자체가 변조될 수 있습니다.
- 적용 방법: 도메인에 맞는 인증서와 개인키를 준비하고, 웹 서버·리버스 프록시·로드 밸런서 또는 애플리케이션에서 TLS 연결을 처리하도록 설정합니다. 인증서 만료와 자동 갱신도 관리해야 합니다.
- HTTP 전환: HTTP 요청을 HTTPS로 리다이렉트할 수 있지만, 최초 HTTP 요청 자체는 암호화되지 않습니다. 브라우저에 HTTPS 사용을 강제하는 HSTS를 함께 고려할 수 있습니다.
- TLS 종료: 로드 밸런서나 리버스 프록시에서 TLS 연결을 처리한 뒤 애플리케이션으로 요청을 전달할 수 있습니다. 이때 프록시와 애플리케이션 사이 구간은 별도로 보호해야 하며, 외부 HTTPS 적용만으로 내부 구간도 암호화되는 것은 아닙니다.
- 주의점: HTTPS는 전송 구간을 보호합니다. 서버에 저장된 데이터의 암호화, 접근 권한 검사, SQL Injection이나 XSS 같은 애플리케이션 취약점은 별도로 대응해야 합니다. 인증서가 유효하다는 이유만으로 해당 사이트의 운영자를 신뢰할 수 있는 것도 아닙니다.

# 3. SSL과 TLS의 개념과 동작 방식

- SSL(Secure Sockets Layer): 네트워크 통신을 암호화하기 위해 만들어진 보안 프로토콜입니다. 기존 SSL 버전은 보안 문제로 사용하지 않으며, 이를 계승한 TLS를 사용합니다.
- TLS(Transport Layer Security): 통신 상대를 인증하고, 전송 데이터의 기밀성과 무결성을 제공하는 프로토콜입니다. HTTPS뿐 아니라 다른 응용 프로토콜의 통신 보호에도 사용할 수 있습니다.
- SSL과 TLS의 관계: TLS는 SSL을 계승해 발전한 별도의 프로토콜 버전 체계입니다. 흔히 말하는 'SSL 인증서'는 실제로 TLS 연결에 사용하는 인증서를 가리키는 경우가 많습니다.
- 인증서: 서버의 공개키와 도메인 등의 정보를 인증 기관(CA)의 전자서명으로 연결한 문서입니다. 클라이언트는 신뢰하는 CA까지의 인증서 체인, 유효기간, 요청한 도메인과의 일치 여부 등을 검증합니다.
- 공개키와 개인키: 공개키는 다른 사람에게 공개할 수 있고, 개인키는 소유자만 보관해야 합니다. 일반적인 TLS 1.3 인증서 기반 연결에서 서버는 개인키로 핸드셰이크 내용에 서명하고, 클라이언트는 인증서의 공개키로 서명을 검증해 개인키 보유 여부를 확인합니다.
- 대칭키 암호화: 암호화와 복호화에 공유된 비밀키를 사용하는 방식입니다. TLS는 비대칭키 기술로 인증과 키 합의를 수행하고, 실제 데이터는 효율적인 대칭키 암호화로 보호합니다. 송신·수신 방향별로 별도의 트래픽 키를 사용합니다.
- 핸드셰이크: 실제 애플리케이션 데이터를 주고받기 전에 사용할 보안 설정을 협상하고, 상대를 인증하며, 통신에 사용할 키를 준비하는 과정입니다. 아래는 세션 재개를 제외한 일반적인 TLS 1.3 인증서 기반 연결의 흐름입니다.
- 1단계 — ClientHello: 클라이언트가 지원하는 TLS 버전과 암호화 방식, 키 합의에 사용할 공개값 등을 서버에 보냅니다.
- 2단계 — ServerHello와 키 합의: 서버가 사용할 버전과 암호화 방식을 선택하고 자신의 키 합의 공개값을 보냅니다. 양쪽은 ECDHE 등의 방식으로 공유 비밀을 계산하고, 여기서 핸드셰이크를 보호할 키를 도출합니다. 비밀키 자체를 네트워크로 보내는 방식은 아닙니다.
- 3단계 — 서버 인증: 서버가 인증서와 핸드셰이크 내용에 대한 전자서명, Finished 메시지를 보냅니다. TLS 1.3에서는 이 단계의 메시지도 암호화됩니다. 클라이언트는 인증서와 서명, Finished를 검증합니다.
- 4단계 — 핸드셰이크 완료: 클라이언트도 Finished 메시지를 보내 서버가 검증하도록 합니다. 양쪽은 핸드셰이크에서 도출한 애플리케이션 트래픽 키로 HTTP 요청·응답을 보호합니다.
- 인증서와 키 합의의 차이: 인증서는 상대의 신원을 검증하는 데 사용하고, 키 합의는 양쪽이 같은 공유 비밀을 얻는 과정입니다. TLS 1.3을 '인증서의 공개키로 대칭키를 암호화해서 서버에 보낸다'고 설명하면 정확하지 않습니다.
- 상호 TLS(mTLS): 일반적인 HTTPS에서는 서버를 인증하며, mTLS에서는 클라이언트도 인증서를 제시해 서버가 검증합니다. 일반적인 웹사이트의 아이디·비밀번호 로그인과는 다른 인증 방식입니다.
- 주의점: TLS 버전, 인증 방식, 세션 재개 여부에 따라 실제 메시지와 순서는 달라질 수 있습니다. 서버 개인키가 유출되지 않도록 관리하고, 클라이언트의 인증서 검증을 끄지 않아야 합니다.
